# v1 协议对工控上位机场景的适用性分析

> 2026-11-12
> 依据：`docs/ws-protocol-v1.md`（协议）、`apps/v1/base`（实现）、
> EPH205 模块与 CEF 客户端的实际落地经验。
> 与 `docs/v1-retrospective.md` 的分工：那份讲"设计 vs 实现的差距"，
> 这份只回答一个问题——**它够不够工控上位机用**。

---

## 结论先说

**够用，但够用的是"通道"，不是"语义"。**

v1 把"怎么把字节可靠、有序、可控地送过去"这一层做得很好：会话、帧、
背压、序号、安全联锁、作业，都是工控上位机真正需要的东西，而且在
205 上跑通了。

它没有做的是**工控数据的语义层**：每个值可不可信（质量）、出事了怎么知道
（报警）、事后怎么复盘（历史回填）、谁干的（审计）。这四件事现在被完整地
推给了"业务模块自定义 payload"。对单个项目（比如 205）没问题；对"任何
工控项目都能用"就有问题——每个项目都得重新发明一遍质量码和报警模型。

一句话：**它是一条好总线，还不是一套工控数据模型。**

---

## 一、判断标准：工控上位机到底要什么

把需求分四类，后面逐条对：

| 类别 | 具体需求 |
|---|---|
| **控制** | 参数下发、启停、点动、参数包原子生效、命令可重试、急停 |
| **数据** | 实时采集、时间戳、完整性可判、背压、单位/量纲、质量、报警、历史 |
| **会话** | 单机单会话、断线安全、权限、审计、重连恢复 |
| **工程** | 离线部署、版本协商、可诊断、配置持久化、可仿真 |

---

## 二、逐项核对

### A. 控制

| 需求 | v1 现状 | 判断 |
|---|---|---|
| 参数下发 | `PUT/PATCH /params/{scope}` + revision | **够用**。205 的线制/量程就是这么改的 |
| 启停 | `modules/{ns}/start|stop`、jobs | **够用** |
| 点动 / 连续设定值 | 只有 HTTP，每个动作一次往返 | **不够**。本地 RTT 尚可，但"按住点动"这种要 20~50 Hz 的操作，HTTP 语义不对（要做请求合并/去抖，很别扭） |
| 参数包原子生效 | PUT 整体替换，但没有"同时生效"的语义 | **不够**。先设量程再设线制，中间那段中间态在真机上是不安全的 |
| 命令可重试 | HTTP 天然可重试，但设备命令不一定幂等 | **不够**。没有 request-id / 去重窗口，超时重发可能把"启动"发两次 |
| 急停 | 只有"断开 WS → 底座 SAFE_STOP" | **勉强**。断开是兜底，不是急停；急停应该是一个明确的、最高优先级的端点 |

### B. 数据

| 需求 | v1 现状 | 判断 |
|---|---|---|
| 实时采集 | WS 二进制帧 + 订阅 + credit | **够用**。205 的实时读数就是这么推的 |
| 时间戳 | 帧级 `ts` + 每条记录自带 `ts` | **够用**（单设备）。跨设备对齐不够，见 §C |
| 完整性可判 | `seq` 递增 + `core.overrun` 设计 | **设计够，实现没有**。现在 seq 是发送时分配的，缺口语义不成立 |
| 背压 | 环形缓冲 + credit + overrun 上报 | **设计够，实现缺位**。底座把"有没有数据"交给模块 `Produce()`，自己没有缓冲，等于把流控责任推给了业务 |
| 单位 / 量纲 | META 里有 `meta`，但**没有强制约定** | **不够**。工控数据必须带单位（Ω/V/mA/°C），现在每个模块自己写字符串，客户端只能硬编码 |
| 质量 | payload 里自己表达（205 用 Status 枚举 + NaN） | **不够，且这是最大的缺口**。见 §三 |
| 报警 | 事件通道可发任意 JSON | **不够**。没有等级、没有确认、没有去抖、没有恢复语义 |
| 历史 | 实时流 + 业务自己落库 | **不够**。没有"查询某个时间区间"的标准端点，趋势图回填只能各做各的 |

### C. 会话与运行

| 需求 | v1 现状 | 判断 |
|---|---|---|
| 单机单会话 | 1:1，硬约束 | **够用**，而且是对的（对上位机来说状态越简单越好） |
| 断线安全 | `OnClose → SafeStop → 模块 Stop()` | **很好**。20 行代码堵死"浏览器崩了设备还在输出" |
| 权限 | 角色 + `AdminOnly` + 服务端 403 | **够用** |
| 审计 | 无 | **不够**。谁在什么时候下了什么命令、改了什么参数，工控（军工/轨交/医疗）是必查项 |
| 重连恢复 | 新会话 = 从零开始 | **不够**。断线重连后拿不到中断前的状态/数据，只能靠业务自己补 |
| 多人观察 | 1:1 排他 | **场景相关**。单机操作不需要；"一人操作 + 一人旁观/投屏"就需要只读观察者 |

### D. 工程

| 需求 | v1 现状 | 判断 |
|---|---|---|
| 离线部署 | 单 exe + 静态文件，零外部依赖 | **很好**，这是这套方案最大的工程优势 |
| 版本协商 | `/api/v1` + caps | **够用**，但缺"最低客户端版本"与废弃策略 |
| 可诊断 | `/logs` 是字符串数组 | **不够**。没有级别、模块、请求 id，出问题只能翻文本 |
| 配置持久化 | `config/{scope}` + revision | **基本够**。缺 schema 校验和回滚 |
| 可仿真 | com0com + 模块内仿真 | 协议无关，但底座允许"仿真和真机走同一条链路"，这一点很关键 |

---

## 三、最大的缺口：质量（quality）

工控和普通 Web 应用最大的区别是：**一个数值不等于一个"真值"。**

- ADC 读到的是 3.3V，但这个点可能已经**超量程**、可能**开路**、可能
  **传感器饱和**、可能**还没稳定**；
- 上位机如果把这些值一视同仁画到趋势图上，操作员会做出错误判断。

205 里我们是这样表达的：

```cpp
struct Reading {
  Status status;      // kOk / kOverRange / kAdcTimeout / ...
  float ohms;         // 失败时为 NaN
};
```

这个东西**每个工控项目都要有，而且应该长得一样**。但 v1 里它是业务自己
定义的 payload 字段，意味着：

- 换个项目，客户端要重新知道"哪个字段是状态、哪个值表示无效"；
- 同一个项目里，不同流的质量表达可能不一致；
- 底座想做一个"通用的趋势/报警/落库"，无从下手——因为它不认识质量。

**建议**：在协议层加一个最小约定，而不是引入完整信息模型：

```text
META.layout 里每个字段声明 {type, unit, scale}
record payload 里保留一个质量字：
  q = 0 表示好值；非 0 是位标志（超量程/开路/超时/未稳定…），
      位含义由 META.quality_bits 声明
```

代价很小（一个保留字段 + 一段 META 约定），收益是**底座和客户端第一次
可以对"数据是否可信"达成共识**。

---

## 四、第二缺口：报警与事件

现在的 `event` 通道能发任意 JSON，够灵活，但不够"工控"：

| 报警应有的 | v1 |
|---|---|
| 等级（提示/警告/严重/紧急） | 无约定 |
| 触发条件与恢复条件 | 业务自己判断 |
| 去抖（连续 N 次才报） | 无 |
| 确认（操作员 ack） | 无 |
| 快照（当前所有活动报警） | 无 |

没有这些，"报警"就退化成"页面上的一个红字"。而工控现场对报警的要求是
**不能漏、不能刷屏、必须可确认、必须留痕**。

---

## 五、第三缺口：历史与回填

实时流解决"现在"，历史解决"刚才"。工控上位机几乎必然要做趋势图，
趋势图一打开就要回填最近几分钟/几小时——现在协议里没有这个端点，
每个项目自己去读 SQLite 再自己定格式。

**建议**：不一定要做完整的 HDA（OPC UA 的历史访问），只需要一个最小的：

```text
GET /api/v1/streams/{id}/history?from=...&to=...&maxPoints=N
→ 降采样后的记录（复用 record 容器）
```

底座不实现存储，只定义**查询形状**，由模块提供。

---

## 六、明确"不需要"的（避免过度设计）

这点和上面的缺口一样重要，否则协议会膨胀成 OPC UA：

| 不做 | 理由 |
|---|---|
| 通用信息模型（节点树、类型系统） | 上位机 UI 是自己写的，不需要通用建模；205 的点表就是数组 |
| 多客户端/多租户 | 单机上位机天然 1:1；要看板就加"只读观察者"，不要改成通用多客户端 |
| 内置 TLS / 证书体系 | 本机回环，前面套一层反向代理即可 |
| 服务端历史数据库 | 存储是业务的事（205 用 JSONL），协议只定查询形状 |
| 完整的报警管理系统 | 只补"报警事件的最小字段约定"，不做报警服务器 |

## 七、和 OPC UA / Sparkplug 比，位置在哪

| 维度 | OPC UA | MQTT Sparkplug B | v1 |
|---|---|---|---|
| 定位 | 设备信息模型 + 服务 | 工业 MQTT 的命名/生命周期 | 上位机 ↔ 本地服务 |
| 质量码 | 内建 | 内建（metric 带 quality） | **缺** |
| 报警 | 有（Condition） | 无（靠 payload） | **缺** |
| 历史 | HDA | 无 | **缺** |
| 订阅/背压 | 有（PublishingInterval） | 无 | 有（credit，设计完整） |
| 部署 | SDK/服务，重 | broker + 客户端 | 单 exe，最轻 |
| 学习成本 | 高 | 中 | 低（一台设备两小时能上手） |

v1 的合理定位是：**比 OPC UA 轻一个数量级，但把 OPC UA 里"上位机真的会用到的
那三样"（质量、报警字段、历史查询形状）补上。** 不需要把整套信息模型搬过来。

## 八、如果补，改动面有多大

| 项 | 改哪里 | 量级 |
|---|---|---|
| 质量字约定 | 文档 + META 约定 + 205 模块的 payload | 小（文档为主） |
| 报警事件的最小字段 | 文档 + 一条事件约定 | 小 |
| 历史查询端点 | 底座加一个路由 + 模块接口加一个方法 | 中（~100 行 + 模块实现） |
| 审计 | 底座在命令分派处记录（谁/何时/什么/结果） | 小（~60 行） |
| WS 命令通道（点动） | 底座加一条上行 JSON 协议 + 模块分派复用 | 中（~150 行） |
| 参数包原子生效 | 参数接口加 `apply_at` 语义 | 中（涉及各模块实现） |
| 急停端点 | 底座加 `POST /estop` → 所有模块 Stop | 小（~30 行） |
| 环形缓冲 + overrun | 底座接管 `Produce` 的写入端 | 大（前面复盘里说过） |

前四项加起来一天多就能落地，且**不改动任何现有接口**——这是最划算的一批。

---

## 九、一页结论

| 问题 | 回答 |
|---|---|
| 传输层够不够？ | **够，而且做得好**。会话、帧、背压设计、SAFE_STOP、作业模型都贴合上位机 |
| 数据语义够不够？ | **不够**。缺质量、报警字段、历史回填，这三样是工控上位机的日常 |
| 是不是要变成 OPC UA？ | **不要**。补最小语义约定，保住"轻"这个最大优势 |
| 现在能不能用？ | **能**。205 已经在真串口链路上跑通了完整闭环 |
| 下一步最该做什么？ | 质量字约定 → 报警字段 → 历史查询 → 审计。四项都不改现有接口 |

一句话收尾：

> v1 已经把"总线"这件事做对了。接下来要补的不是带宽、不是并发，
> 而是**让数据自己说清楚"我可不可信"**——这恰恰是工控和普通 Web 的分水岭。
