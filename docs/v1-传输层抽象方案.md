# v1 传输层抽象：同一核心，HTTP/WS 与 QWidget 直连

> 2026-11-13（v2：修订）
> **修订说明**：上一版把"进程内"理解成了"页面通过 JS 桥访问核心"，
> 方向错了。这一版按实际需求重写——宿主是**原生 Qt Widgets 界面**，
> 没有网页参与，也就没有桥、没有 scheme、没有页面侧的 transport 层。

---

## 结论

**可行，而且比"桥"那一版更简单。**

因为 QWidget 直接调 C++，本来就不需要网络，也不需要序列化协议。
真正要做的只有两件事：

1. 把 `V1Server` 拆成 **Core（无 socket）** + **HTTP/WS 适配器**；
2. 给 Qt 写一层**门面**：向上提供类型化的方法调用和 Qt 信号，
   向下把请求塞进 `Core::Handle()`、把下行事件转成信号。

**强烈建议：即使最终只交付 Qt 界面，HTTP/WS 那层也留着**——它现在是整个项目的
自动化测试通道（`tools/eph205_api_test.py`、EdgeDriver 脚本全靠它），
而且将来要做远程诊断/浏览器访问时不用再改。

---

## 一、这和上一版的区别

| | 上一版（错的方向） | 这一版 |
|---|---|---|
| 宿主 | CEF/Qt 里跑网页 | 原生 QWidget |
| 进程内通道 | JS 桥（cefQuery / QWebChannel） | **C++ 直接函数调用** |
| 页面侧改动 | 加 `transport.js` | **没有页面** |
| 下行数据 | 桥回调推给 JS | **Qt 信号** |
| 需要自定义 scheme | 是（页面从 app:// 加载） | **否** |
| 预览/调试 | DevTools | Qt Creator + 日志 |

## 二、目标结构

```text
        ┌──────────────────┐        ┌──────────────────────┐
        │  浏览器 / CEF     │        │   Qt Widgets 界面     │
        │  (现有 web UI)    │        │   (新写，或改造旧界面) │
        └────────┬─────────┘        └───────────┬──────────┘
                 │ HTTP / WS                    │ 方法调用 + Qt 信号
        ┌────────▼─────────┐        ┌───────────▼──────────┐
        │ HttpWsAdapter     │        │ QtFacade              │
        │ mongoose + 端口    │        │ Eph205Device 之类      │
        └────────┬─────────┘        └───────────┬──────────┘
                 │  Request/Response             │  Request/Response
                 │  EventSink                    │  EventSink → 信号
                 └──────────────┬────────────────┘
                        ┌───────▼────────┐
                        │   v1::Core      │  模块/会话/订阅/作业/参数/配置
                        │  （无 socket）   │
                        └────────────────┘
```

关键点：**上下行不对称**。

- **上行（请求）**：Adapter 是拉模式——HTTP 适配器解析请求后调
  `Core::Handle()`；Qt 门面也是直接调 `Core::Handle()`。同一条路径。
- **下行（事件/数据）**：Core 通过 `EventSink` 接口往外推——HTTP 适配器实现成
  WS 帧，Qt 门面实现成 Qt 信号。

所以对 Qt 来说，需要抽象的只有**下行**；上行天然就是函数调用。

## 三、接口

### 3.1 核心侧

```cpp
namespace v1 {

struct Request {
  std::string method, path, query, body;
  std::map<std::string, std::string> headers;
};
struct Response {
  int status = 200;
  std::string content_type = "application/json";
  std::string body;
};

// 下行出口。Core 只认这个，不认 WS、也不认 Qt
class EventSink {
 public:
  virtual ~EventSink() = default;
  virtual void OnEvent(const std::string& name, const nlohmann::json& payload) = 0;
  virtual void OnFrame(uint32_t stream_id, const std::vector<uint8_t>& frame) = 0;
  virtual void OnClosed(int code, const std::string& reason) = 0;
};

class Core {
 public:
  void RegisterModule(Module* m);

  void Attach(EventSink* sink);   // 建立会话（1:1）
  void Detach();                  // SAFE_STOP + 清会话

  bool Handle(const Request& req, Response& res);   // 原来的 OnHttp 路由主体
  void HandleWsText(const std::string& text);       // credit 等上行文本

  void Tick(uint64_t now_ms);     // 作业事件 + 按订阅推流
  void Ping(uint64_t now_ms);
};

}  // namespace v1
```

`HttpWsAdapter` 持有 `mg_mgr`，实现 `EventSink`（`OnFrame` → `mg_ws_send`）。
`QtFacade` 也实现 `EventSink`，把 `OnEvent/OnFrame` 转成信号。

### 3.2 Qt 侧门面

每个业务模块一个门面类，形状跟着模块走（205 的样子）：

```cpp
class Eph205Device : public QObject {
  Q_OBJECT
 public:
  explicit Eph205Device(v1::Core* core, QObject* parent = nullptr);

  // —— 短命令：同步返回，内部仍有超时保护
  bool connect(const QString& port, v1::eph205::DeviceInfo* info, QString* error);
  bool setParam(int type, int value, QString* error);
  bool getParams(v1::eph205::DeviceParams* out, QString* error);
  bool measure(int p, int n, v1::eph205::Reading* out, QString* error);

  // —— 长命令：异步，结果走信号
  bool startMeasure(const QVector<v1::eph205::TestItem>& items);
  void cancelMeasure();

 signals:
  void stateChanged(const v1::eph205::DeviceState& state);
  void jobProgress(const v1::eph205::JobProgress& progress);
  void readingsReady(const QVector<v1::eph205::Reading>& batch);
  void logLine(const QString& text);
  void errorRaised(int status, const QString& message);
};
```

实现方式很简单——**门面不重写业务逻辑，只做 JSON ↔ 结构体的翻译**：

```cpp
bool Eph205Device::setParam(int type, int value, QString* error) {
  v1::Request req{"POST", "/api/v1/commands/eph205/set_param", "",
                  nlohmann::json{{"type", type}, {"value", value}}.dump(), {}};
  v1::Response res;
  if (!core_->Handle(req, res)) {          // 返回 false = 传输层问题
    if (error) *error = QString::fromStdString(res.body);
    return false;
  }
  if (res.status != 200) {                 // 业务层拒绝
    if (error) *error = QString::fromStdString(extractMsg(res.body));
    return false;
  }
  return true;
}
```

**为什么门面要走 `Handle()` 而不是直接调 `module->Command()`：**
权限（`AdminOnly`）、审计、参数作用域校验、错误码格式全在 `Handle()` 这条路上。
绕过去等于把同一套语义实现两遍，早晚会漂。门面只做"翻译"，不做"决策"。

## 四、Qt 里怎么表达"事件"和"数据"

### 4.1 事件（作业进度、状态、日志）→ 信号

Core 的 `Tick()` 在核心线程上跑，产生事件后调 `EventSink::OnEvent`。
Qt 适配器里转成信号时**必须用队列连接跨线程投递**：

```cpp
void QtEph205Sink::OnEvent(const std::string& name, const nlohmann::json& payload) {
  if (name == "eph205.job.progress") {
    auto progress = parse_progress(payload);
    QMetaObject::invokeMethod(device_, [device = device_, progress] {
      emit device->jobProgress(progress);
    }, Qt::QueuedConnection);          // 关键：别在核心线程里直接 emit
  }
}
```

直接在非 UI 线程 `emit` 会命中 Qt 的断言（或更糟，静默出错）。
`QueuedConnection` 把调用投递到 UI 线程的事件队列，这是 Qt 的标准跨线程写法。

### 4.2 数据（实时读数）→ 看频率决定

两条路，按速率选：

| 速率 | 做法 | 理由 |
|---|---|---|
| < 100 条/秒 | 直接 emit 信号，UI 里往表格/model 追加 | 简单，事件循环扛得住 |
| ≥ 100 条/秒 | **环形缓冲 + QTimer(33~50ms) 拉取** | 每来一条就 post 一次事件，Qt 事件队列会积压，界面反而更卡 |

205 的测量是"每帧最多 62 点、整批 640 点"，属于低频，走信号即可。
将来接振动/波形这类，必须走环形缓冲——这一点和 web 那边用 WS credit 是同一个道理：
**UI 的刷新节奏不应该由数据产生节奏决定。**

环形缓冲的接口建议：

```cpp
// 核心线程写，UI 线程读，用无锁队列或一把小锁
class ReadingBuffer {
 public:
  void Push(const Reading& r);                 // 核心线程
  QVector<Reading> TakeAll();                  // UI 线程，QTimer 里调
};
```

### 4.3 同步还是异步

| 命令 | 建议 | 说明 |
|---|---|---|
| getParams / ports / state | 同步 | 毫秒级，UI 直接等 |
| connect / disconnect | 同步（带 2~5 秒超时） | Qt 里可以接受一次短暂等待，但要给忙碌光标 |
| setParam / measure 单点 | 同步 | 串口一轮 100ms 内 |
| measure 批量 / 标定 / 长时间作业 | **必须异步** | 走 job + 信号，UI 不阻塞 |

判据：**超过 300ms 的一律异步**。UI 线程卡 300ms 以上，操作员能明显感觉到。

## 五、会话与安全停机在纯 Qt 下怎么映射

原来 WS 断开 = 会话结束 = `SafeStop`。纯 Qt 没有 WS 了，映射关系是：

| 原语义 | Qt 里的对应 |
|---|---|
| WS 建连 | 主窗口创建后 `core.Attach(this)` |
| WS 断开 → SAFE_STOP | 主窗口 `closeEvent` / 析构 → `core.Detach()` |
| 心跳判死 | 不需要（进程内没有链路假死） |
| 会话忙 409 | 进程内只可能有一个 UI，天然不会发生 |

**要注意的一点**：`Detach()` 必须能保证"串口关了、作业停了、输出关了"。
205 的 `Eph205Module::Stop()` 已经做了这件事（取消作业、关串口、停仿真），
所以这条链路是现成的——但要在文档和测试里明确：**关窗口 = 停机**。

## 六、两种交付形态怎么共存

三个层次，按需要取舍：

| 形态 | 组成 | 适用 |
|---|---|---|
| **A. 纯 Qt** | Core + QtFacade，不编译 HTTP 适配器 | 只给客户装桌面程序，永远不用浏览器 |
| **B. Qt + HTTP**（推荐） | 同上，HTTP 适配器也编进来（可命令行关闭监听） | 交付 Qt 界面，但保留自动化测试与远程诊断 |
| **C. 浏览器 + HTTP** | 现有形态 | 调试、演示、跨机器访问 |

**推荐 B**。理由很实在：v1 现在所有的自动化（api 测试、EdgeDriver、uth 测试）
都走 HTTP。如果为了"纯 Qt"把这层砍掉，以后每加一个功能就得手点验证一遍。
保留监听不是一个负担——它是开关，可以不监听。

代码组织上就是编译选项：

```cmake
option(V1_WITH_HTTP "编译 HTTP/WS 适配器" ON)
```

## 七、纯 Qt 形态下，v1 的价值重估

这一点值得说清楚，否则容易觉得"既然直接调函数，协议就没用了"。

**仍然有价值的**：

- `Core::Handle` 的**路由与契约**（命令名、参数形状、错误码、权限）是唯一的真相来源，
  Qt 门面和 web 前端都照着它来；
- 作业/进度/取消这套模型，Qt 里同样需要（异步任务 + 进度信号）；
- 参数作用域、配置持久化、Blob、日志——全部复用；
- HTTP 通道作为**测试夹具**，比给每个门面方法写单元测试便宜得多。

**失去意义的**：

- 24 字节帧、seq、credit、分片、WS 关闭码——这些是**线缆上的事**，
  纯 Qt 场景下没有线缆。

所以"v1 协议"在纯 Qt 形态下退化为**内部 API 契约**，而这个契约恰恰是最该保留的部分。

## 八、迁移路径

| 步 | 做什么 | 验收 |
|---|---|---|
| 1 | 从 `V1Server` 抽 `Core`（成员下移、方法改名），`V1Server` 变成 HttpWsAdapter 的薄壳 | 现有全部测试通过，行为零变化 |
| 2 | 加 `EventSink` 接口，`SendEvent/SendFrame` 改走它 | 同上 |
| 3 | 写第一个门面 `Eph205Device` + 一个最小 Qt 页面（连接/测量/结果表） | 手点跑通；HTTP 测试同时仍然通过 |

第 1、2 步是纯重构，半天；第 3 步一天；后面按页面算。

## 九、代价与风险

| 项 | 影响 | 处理 |
|---|---|---|
| **界面要写两遍** | 如果 web 和 Qt 都要维护，这是最大成本 | 先只做一条主线：要么 web 为主线、Qt 逐步补；要么反过来，明确写进计划 |
| 门面样板代码 | 每个命令一个方法 + 一次 JSON 翻译 | 机械劳动；可以先只写界面真正用到的 |
| 跨线程 emit | 忘了 `QueuedConnection` 会偶发崩溃 | 在适配器里统一封装，禁止业务代码直接 emit |
| 高频数据 | 信号风暴 | 环形缓冲 + 定时拉取（见 §4.2） |
| Qt 依赖回流到底座 | 门面一旦写进 `apps/v1`，底座就不"纯 C++"了 | **门面放在独立目录（如 `apps/qt_facade`），Core 保持零 Qt** |

最后一条要强调：v1 底座"零 Qt"是个已经兑现的承诺（CEF 客户端就是零 Qt 的）。
门面可以依赖 Qt，但它必须是**底座的消费者**，不能反向污染。

## 十、一页结论

| 问题 | 回答 |
|---|---|
| 做得到吗 | 做得到，而且比"页面走桥"简单：上行本来就是函数调用，只需抽象下行 |
| 改哪里 | `server.cpp` 拆 Core + HttpWsAdapter；新增 `EventSink`；新增 Qt 门面 |
| Qt 侧要写多少 | 一个模块一个门面类（205 约 300 行）+ 页面 |
| 最大的坑 | 跨线程信号投递、高频数据用信号风暴、界面写两遍 |
| 底座会不会被 Qt 污染 | 不会，只要门面放在独立目录、Core 只认 `EventSink` |
| 建议 | 走"形态 B"：Qt 界面交付，HTTP 层留着当测试通道 |
