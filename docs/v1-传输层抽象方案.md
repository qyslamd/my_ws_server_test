# v1 传输层抽象：同一套核心，两种载体

> 2026-11-13
> 背景：205 现在有两条交付路径——浏览器 + 本地 HTTP/WS 服务端，和 CEF 桌面客户端
> （页面在进程内，但仍走 127.0.0.1 的回环网络）。后者完全没必要开端口。

---

## 结论

**可行，而且改动集中在底座的一个文件（`server.cpp`）。**

关键不是"把网络换成函数调用"这么一句话，而是先把 `V1Server` 拆成两半：

- **Core**：业务中立的核心（模块、会话、订阅、作业、参数、配置、Blob），
  只认"请求→响应"和"下行消息"，不认识任何 socket；
- **Adapter**：承载方式。现在有 `HttpWsAdapter`（mongoose），再加一个
  `BridgeAdapter`（宿主进程内的 JS 桥）。

页面那边同样加一层 `Transport` 抽象：`WebSocketTransport` 和 `BridgeTransport`
共用同一套 `request/send/onmessage` 形状。页面代码一行不用改。

**两个必须注意的设计点**（后面详述）：

1. 桥必须**异步**（带 request id 和回调），不能做成同步函数调用——否则
   "连接设备"这种要 2 秒的命令会冻住 UI 线程。
2. 没有 mongoose 就没有定时器了，`Tick()` 要由宿主驱动（Qt 定时器或专用线程）。

---

## 一、为什么值得做

| 收益 | 说明 |
|---|---|
| **不开端口** | 现在 CEF 客户端会 `listen 127.0.0.1:8791`。企业环境里监听端口会触发防火墙弹窗、被安全软件标记、被运维盘问 |
| **没有端口冲突** | 现在要 8791..8810 顺延，还要单实例互斥。进程内不存在这个问题 |
| **延迟和抖动更低** | 少了 TCP 栈、HTTP 头解析、JSON 序列化一次。实时读数 10 ms 一拍时，这点抖动是能感觉到的 |
| **同一份页面三种宿主** | 浏览器 + 本地服务端、CEF 客户端、嵌进别人的 Qt 程序——页面和协议完全一致 |

反过来，也有一个明确的**不该做**的场景：如果只交付 CEF 客户端、从不做浏览器访问，
那桥是净增复杂度（两套传输要测、调试手段少一半）。见 §十。

## 二、现状：`V1Server` 里哪些是传输，哪些是核心

`apps/v1/base/server.cpp` 现在把这些揉在一个类里：

| 现有成员 | 性质 | 去向 |
|---|---|---|
| `mg_mgr* mgr_`、`mg_timer_add`、`mg_mgr_poll` | 传输 | HttpWsAdapter |
| `OnHttp()` 里的路由分发（`/api/v1/...` 那一大段 if） | **核心** | Core::Handle |
| `OnWsMsg()`（解析 credit 上行） | **核心** | Core::HandleWsMessage |
| `OnWsOpen/OnClose`（建/销会话） | 两者都有 | 拆：会话由 Core 管，建销由 Adapter 通知 |
| `SendEvent` / WS 帧发送 | 传输 | Transport 接口 |
| `Session`/`subs`/`seqs_`/`modules_`/`job_owner_` | **核心** | Core |
| `Tick()`（作业事件 + 按订阅推流） | 半核心 | Core::Tick，由 Adapter 决定何时调 |
| `Ping()`（心跳判死） | 半核心 | Core::Ping，同上 |
| `SafeStop` | **核心** | Core::Detach |
| 静态文件 `www/v1` | 传输相关 | HttpWsAdapter 直接发；Bridge 用自定义 scheme |

拆完之后 `Core` 里不该出现 `mg_` 开头的任何东西，也不该 include mongoose。

## 三、目标结构

```text
                    ┌────────────────────────────┐
   浏览器 / CEF ───►│  Transport（页面侧 JS）      │
                    │  WebSocketTransport          │
                    │  BridgeTransport             │
                    └────────────┬───────────────┘
                                 │ 请求/响应 + 下行消息
              ┌──────────────────┴───────────────────┐
              │                                      │
   ┌──────────▼──────────┐              ┌────────────▼────────────┐
   │ HttpWsAdapter        │              │ BridgeAdapter            │
   │ mongoose + 回环端口   │              │ JS 桥（CefMessageRouter /│
   │ 静态文件             │              │ QWebChannel）            │
   └──────────┬──────────┘              └────────────┬────────────┘
              │        Transport 接口                │
              └──────────────────┬───────────────────┘
                                 │
                        ┌────────▼────────┐
                        │   v1::Core       │  模块/会话/订阅/作业/参数/配置/Blob
                        │  （无 socket）    │
                        └─────────────────┘
```

`Core` 同时可以被原生 C++ 直接调用（第三种消费者），见 §七。

## 四、接口定义

### 4.1 C++ 侧

```cpp
namespace v1 {

struct Request {
  std::string method;                 // GET/POST/PUT/PATCH/DELETE
  std::string path;                   // /api/v1/commands/eph205/measure
  std::string query;                  // a=1&b=2（可为空）
  std::string body;                   // JSON 或二进制
  std::map<std::string, std::string> headers;
};

struct Response {
  int status = 200;
  std::string content_type = "application/json";
  std::string body;
};

// 下行：核心 → 宿主。Adapter 负责把这三样变成 WS 帧或桥回调
class Transport {
 public:
  virtual ~Transport() = default;
  virtual void SendEvent(const std::string& json) = 0;      // 文本事件
  virtual void SendBinary(const std::vector<uint8_t>&) = 0; // 二进制帧
  virtual void Close(int code, const std::string& reason) = 0;
  virtual bool connected() const = 0;
};

class Core {
 public:
  void RegisterModule(Module* m);
  void RegisterMediaSource(MediaSource* s);

  // 会话（1:1）
  void Attach(Transport* t);        // 建立会话；已有会话时返回 false
  void Detach();                    // 断开：SAFE_STOP + 清会话
  bool attached() const;

  // 请求路径：原来的 OnHttp 路由主体
  bool Handle(const Request& req, Response& res);

  // 上行：credit 等 WS 文本消息（保留原格式，便于两种载体共用）
  void HandleWsText(const std::string& text);

  // 节拍：作业事件、按订阅推流、心跳
  void Tick(uint64_t now_ms);
  void Ping(uint64_t now_ms);

  Config& config();  Blobs& blobs();  // 需要落盘的资源
};

}  // namespace v1
```

`HttpWsAdapter` 持有 `mg_mgr` 和 `Core`，在 `MG_EV_HTTP_MSG` 里组一个 `Request`
调 `Handle`，再把 `Response` 写回去；在 `Tick` 定时器里调 `core_.Tick(now)`。
它实现 `Transport`，`SendBinary` 就是 `mg_ws_send(..., WEBSOCKET_OP_BINARY)`。

`BridgeAdapter` 不持有任何 socket，只持有一个 JS 桥对象。

### 4.2 页面侧

现在 `lib/api.js` 直接 `fetch` + `new WebSocket`。加一层：

```js
// lib/transport.js
export class HttpWsTransport {
  async request(method, path, body) { /* fetch，带 X-Session-Id */ }
  open(onFrame, onEvent) { /* new WebSocket(...) */ }
  send(data) { /* ws.send */ }
}

export class BridgeTransport {
  async request(method, path, body) {
    return window.v1host.request(method, path,
      body === undefined ? null : JSON.stringify(body));
  }
  open(onFrame, onEvent) {
    window.v1host.onBinary = (b64) => onFrame(base64ToArrayBuffer(b64));
    window.v1host.onEvent  = (json) => onEvent(JSON.parse(json));
  }
  send(data) { window.v1host.send(base64Encode(data)); }
}
```

`api.js` 只改一行：`const transport = createTransport()`，其余不动。
页面业务代码零改动。

## 五、桥怎么选、二进制怎么过

| 宿主 | 桥 | 说明 |
|---|---|---|
| CEF（我们的客户端） | `CefMessageRouter`（JS `window.cefQuery`） | CEF 自带，天然请求/响应，回调自动回 UI 线程 |
| Qt WebEngine | `QWebChannel` | Qt 官方，signal/slot 直通 |
| QCefView（YiGuai 那套） | `cefQuery` 封装 | 同上 |

**二进制**：`CefMessageRouter` 只走字符串。第一版用 base64（+33%），
按 205 的实时读数（每帧几条 JSON，最大约几 KB）完全够；真要跑高频大帧，
再换自定义 `CefV8Handler` 直接收 `ArrayBuffer`——接口不用变，只换实现。

**上下行都要异步**：

```text
JS:  v1host.request(id, "POST", path, body)     // 立即返回
C++: 处理完 → v1host.onResponse(id, status, contentType, body)  // 回调
```

理由见 §六。

## 六、线程与节拍：这是唯一真正要小心的地方

现在 HTTP 服务端跑在自己的线程上，`Core` 里的阻塞操作（205 的 `RunSync`
等串口，最长几秒）不会影响 UI。

**进程内如果没有这条线程，桥调用会落在 UI 线程上，"连接设备"就会把界面冻 2 秒。**

所以规则定死：

1. **`Core` 永远跑在它自己的线程上**（Adapter 负责）。桥收到 JS 调用后
   打包成 Request 投递过去，处理完再回调 JS。
2. **UI 线程只做编解码和投递**，永远不等 Core。
3. **`Tick` 也由 Adapter 驱动**，但要在 Core 线程上跑：BridgeAdapter 用一个
   `std::thread` + `sleep(10ms)`，或者由宿主定时器 `Post` 过去。
4. **下行消息从 Core 线程发出**时，Adapter 必须把它转投到 UI 线程再碰桥
   （CEF 的 MessageRouter 有 `CefPostTask(TID_UI, ...)`）。

这四条和现在 HTTP 版的时序**完全一致**，所以模块侧一行不用改——
205 的 worker 线程、RunSync 超时、JobTick 都照旧。

## 七、顺带得到的第三种消费者：原生 C++

`Core::Handle(Request, Response)` 是纯 C++ 接口。所以同一个核心可以：

- 给 HTTP/WS 用（浏览器）；
- 给桥用（CEF/Qt 里的页面）；
- **直接被 Qt Widgets 调用**（不写页面，纯 C++ 界面）：

```cpp
v1::Request req{"POST", "/api/v1/commands/eph205/measure", "", R"({"p":1,"n":2})", {}};
v1::Response res;
core.Handle(req, res);       // res.body 就是 JSON
```

这一点对"老项目改造"很有用：已有的 Qt 界面可以一段段换过来，
不用一次性改成 web。

## 八、静态资源与自定义 scheme

HTTP 适配器已经会发 `www/v1`。进程内没有 HTTP，页面从哪来？

用自定义 scheme（YiGuai 里就有现成的 `ClientSchemeHandler` 写法）：

```text
app://eph205/index.html
app://eph205/lib/api.js
```

`CefRegisterSchemeHandlerFactory` 注册一个 handler，`Open/Read` 时
**直接查 Core 的资源表**（或者查嵌在 exe 里的资源）。这样：

- 页面不需要任何本地服务器；
- 资源可以嵌进 exe，客户看不到目录；
- 和 `--www=<dir>` 的调试模式并存（scheme handler 优先查外部目录，没有就查内嵌）。

## 九、迁移路径：四步，每步都保持现有 HTTP 可用

| 步 | 做什么 | 验收 |
|---|---|---|
| 1 | 从 `V1Server` 抽出 `Core`（成员下移、方法改名），`V1Server` 变成 `HttpWsAdapter` 的薄壳 | 所有现有测试通过，行为零变化 |
| 2 | 加 `Transport` 接口，`SendEvent/SendBinary` 改走它 | 同上 |
| 3 | 页面加 `lib/transport.js`，`api.js` 改一行。默认仍是 WebSocket | 浏览器里行为不变；`?transport=bridge` 可切换 |
| 4 | 加 `BridgeAdapter` + CEF 方案里的 `CefMessageRouter`；CFE 客户端默认走桥，保留 `--http` 开关回退 | 同一套 e2e 脚本跑两遍（桥 / HTTP） |

前两步是纯重构，风险最低；第三、四步才引入新东西。

**测试策略**：`tools/cef_test/eph205_client_check.py` 那套断言不依赖传输方式
（都是在页面里查 DOM），所以换桥之后原样能跑——这本身就是抽象是否干净的判据。

## 十、代价与风险

| 项 | 影响 | 处理 |
|---|---|---|
| 两套传输要测 | 测试矩阵翻倍 | e2e 脚本参数化跑两遍；关键的只有主链路 |
| 调试手段变少 | 桥里没有 DevTools 的 Network 面板可看 | Adapter 里加一个"消息镜像日志"（README 里给格式），可选开 |
| 桥的吞吐上限 | base64 + 字符串编解码，比 WS 慢 | 205 的实时读数远没到上限；高频大帧再换二进制通道 |
| CEF 版本的 API 依赖 | MessageRouter 在 CEF 各版本稳定 | 低 |
| 页面要判断宿主 | 多一个分支 | 只在 `transport.js` 一处 |

## 十一、什么时候**不**该做

- 如果这个产品永远只以 CEF 客户端形态交付、不给浏览器访问——那桥是净增复杂度，
  保持现在的回环端口更简单（反正已经跑通了）。
- 如果未来要做"多人看同一个设备"（多客户端），进程内桥天然只服务一个页面，
  那种场景还是需要真服务器。

**判断标准**：只要"同一份页面既要在浏览器打开、又要嵌进客户端"这个需求还在，
这层抽象就值得做；如果只剩一种形态，就不值得。

## 十二、一页结论

| 问题 | 回答 |
|---|---|
| 做得到吗 | 做得到。核心本来就没碰 socket，缺的只是一层显式的 `Transport` |
| 改哪里 | `server.cpp` 拆成 Core + HttpWsAdapter；新增 BridgeAdapter；页面加 `transport.js` |
| 最大风险 | 线程模型。**Core 必须留在自己的线程，桥必须异步**，否则 UI 会被阻塞 |
| 改多少 | 步骤 1-2 是纯重构（半天），3-4 各一天；现有 205 的 e2e 可直接复用 |
| 值不值 | 取决于是否长期维护"浏览器 + 客户端"两种形态。是，就值 |
