# 双前端策略：Qt QWidget 与 Web 共用一套内核

> 2026-11-13（v2：补全需求清单与实现路径）
> 背景：CEF 这条路线传统客户未必接受，团队也没有先例。设想是——同时支持
> 原生 Qt 界面和 Web 界面，核心保持零 Qt，随时可切换前端；先用 Qt 验证真实功能，
> 验证好了 Web 那边再收尾。

---

## 一、意图拆解

按重要程度排，这件事想要的是三样：

1. **兜底**：客户不接受浏览器/嵌入式引擎时，有原生 Qt 版本可交；
2. **降风险**：核心逻辑在熟悉的工具链（Qt Creator）里验证和排障；
3. **复用**：设备协议、作业、判定、存储只写一遍，两个前端共享。

"Qt 验证完，Web 调一下就好"是这套策略的**推论**，不是它的收益——
下面 §5 会说明为什么这个推论需要修正。

---

## 二、结论

**策略成立。核心一套、界面两套；Qt 负责兜底和排障，Web 负责体验和演示。**

三个要点先摆出来：

- 收益排序是 **兜底 > 降风险 > 复用**，不是"开发量减半"；
- **对核心的信心来自 HTTP 层自动化测试，不是来自第二个 UI**；
- 两端共享的是**核心**，不共享**表现**，所以 Web 侧的表现层风险 Qt 测不到。

---

## 三、需求清单（可验收）

下面十条是这条策略要满足的需求。每条都写了"怎么验收"，避免变成口号。

| # | 需求 | 为什么 | 验收方式 |
|---|---|---|---|
| **R1** | 核心零 Qt | 否则第二个前端要重写核心，第三个前端就别想了 | `apps/v1/base` 下 `grep -r Qt` 为空；MSVC 编译不链接任何 Qt 库 |
| **R2** | 同一核心支撑两个前端 | 业务逻辑只写一遍 | 同一个 `Core` 同时被 HTTP 适配器和 Qt 门面实例化，两端行为一致 |
| **R3** | 前端可切换，且不改核心 | "随时切"的前提 | 同一份提交，分别构建 web 版和 Qt 版，核心代码零差异 |
| **R4** | Qt 版可交付（最小闭环） | 兜底要真的能拿出来 | 能连接、能测、能显示结果、能导出 CSV，无需 web |
| **R5** | 核心行为由 UI 无关的测试保证 | 手动点界面覆盖不到全链路 | 现有 `eph205_api_test.py` / `eph205_e2e.py` 每次改动全绿 |
| **R6** | 两端能力可对照 | 避免"到底以哪个为准" | 维护一张能力矩阵，对外只承诺核心契约 |
| **R7** | 排障可及 | 出问题要能断到现场 | Qt 侧可断点；web 侧可用 DevTools；核心日志统一格式 |
| **R8** | 渐进交付 | 兜底能力不能等全部做完 | P1 阶段就能演示，后续按页补 |
| **R9** | 门面不污染核心 | 保持 R1 | 门面放独立目录；`Core` 只认 `EventSink` 接口 |
| **R10** | 构建可选 | 交付形态按客户定 | 编译开关：HTTP 适配器可关监听；Qt 前端可选编译 |

## 四、架构：三层分工

不要把两个 UI 当平等公民。分成三层，职责写死：

```text
┌──────────────────────────────────────────────────────┐
│ 表达层   Web UI              Qt UI                    │
│         呈现 + 交互           呈现 + 交互               │
│         两个实现，允许不同步   允许一端先有              │
├──────────────────────────────────────────────────────┤
│ 契约层   Core 的命令 / 参数 / 作业 / 错误码             │
│         唯一真相来源；用 HTTP 脚本测（与 UI 无关）       │
├──────────────────────────────────────────────────────┤
│ 内核     v1::Core + 业务模块（零 Qt、零浏览器）          │
└──────────────────────────────────────────────────────┘
```

- **契约层**是唯一必须两端同步的地方；
- **表达层**允许不同步，但要有能力矩阵兜住对外口径。

上下行不对称，这是实现上的关键：

```text
上行（请求）：HTTP 适配器 → Core::Handle()
              Qt 门面    → Core::Handle()      ← 同一条路径
下行（事件）：Core → EventSink → { WS 帧 | Qt 信号 }
```

所以对 Qt 来说，需要抽象的只有**下行**。

## 五、对"Qt 验证核心、Web 只做表现"的修正

这句话对一半：

- **对的一半**：业务逻辑、协议、判定、存储，在 Qt 上验证一次就够了，
  Web 那边不用重新验证；
- **需要修正的一半**：Web 的表现层风险，Qt 一样都测不到。

| Web 独有风险 | 例子 |
|---|---|
| 布局 | 1024×768 表格溢出、高 DPI 错位 |
| 交互 | 输入法、焦点、拖拽、快捷键 |
| 时序 | 事件风暴、重绘卡顿、断线重连 |
| 环境 | CEF 版本、GPU 不可用、字体缺失 |

**准确的说法：核心验证一次，两端各自只承担表现层风险。**
Web 前端不是"调一下"，是一次完整的表现层实现——只是不担业务逻辑风险。

### 关于"心里没底"

这条最该认真对待，但解法要换：**两个 UI 不能给你对核心的信心。**

手动点界面十遍，覆盖的是你想到的十条路径；HTTP 脚本每次跑，覆盖的是全链路
（登录 → 连接 → 导入 → 测量 → 落库 → 导出）。而且这套脚本不依赖任何 UI——
这正是它值钱的地方。

所以三个东西的定位：

```text
核心 + HTTP 适配器   →  脚本化的信心来源（已完成）
Qt 界面             →  兜底交付 + 熟悉的排障入口
Web 界面            →  面向接受浏览器的客户（205 已有）
```

## 六、接口契约（实现前先定死）

### 6.1 核心侧

```cpp
struct Request  { std::string method, path, query, body; Headers headers; };
struct Response { int status; std::string content_type, body; };

class EventSink {                       // 下行出口，Core 只认它
 public:
  virtual void OnEvent(const std::string& name, const json& payload) = 0;
  virtual void OnFrame(uint32_t stream_id, const std::vector<uint8_t>&) = 0;
  virtual void OnClosed(int code, const std::string& reason) = 0;
};

class Core {
 public:
  void RegisterModule(Module*);
  void Attach(EventSink*);              // 建会话（1:1）
  void Detach();                        // SAFE_STOP
  bool Handle(const Request&, Response&);
  void HandleWsText(const std::string&);
  void Tick(uint64_t now_ms);
};
```

`apps/v1/base` 下不出现任何 `mg_*` 以外的第三方，也不出现任何 `Q*` 类型。

### 6.2 Qt 门面规范（四条硬规矩）

1. **只翻译，不决策**：权限、参数校验、错误码格式全在 `Core::Handle()` 里。
   门面只做 JSON ↔ 结构体转换。
2. **超时一视同仁**：短命令同步（内部仍有超时），超过 300 ms 的一律异步
   （走 job + 信号）。
3. **跨线程只走队列**：Core 线程产生的事件，必须
   `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` 投到 UI 线程再 emit。
4. **高频数据不进信号**：≥100 条/秒用环形缓冲 + `QTimer` 拉取。

## 七、实现路径

| 阶段 | 内容 | 产物 | 验收 | 估时 |
|---|---|---|---|---|
| **P0** | 从 `V1Server` 抽 `Core` + `EventSink`；`V1Server` 变成 HTTP 适配器薄壳 | 重构后的底座 | 现有 HTTP/自动化测试全绿，行为零变化 | 0.5 天 |
| **P1** | `Eph205Device` 门面 + Qt 最小页面（连接/测量/结果/导出 CSV） | **可演示、可兜底的 Qt 版** | 手点跑通真串口链路；HTTP 测试同时全绿 | 1 天 |
| **P2** | 补 Qt 页面：调试、历史/对比、工具；实时读数用环形缓冲 + 定时刷新 | Qt 版功能对齐（除三维） | 对照能力矩阵逐项验收 | 2–3 天 |
| **P3** | 一致性保障：能力矩阵入库、Qt 侧最小 `QtTest` 冒烟（连接→单点→结果） | 回归基线 | 两端各跑一遍、都绿 | 1 天 |
| **P4** | 构建形态：`-DV1_WITH_HTTP=ON/OFF`、Qt 前端可选编译、交付目录布局 | 三种构建配置 | 纯 Qt 构建的进程不监听端口，功能完整 | 0.5 天 |
| **P5** | （可选）按客户反馈打磨 Web 端 | — | — | — |

**P1 是分水岭**：做完 P1，"客户不接受浏览器"这件事就不再是风险。
所以顺序上宁可 P1 做得粗一点（只有连接和测量），也不要先做漂亮的完整 Qt 界面。

## 八、成本与风险

### 成本

| 部分 | 行数量级 | 状态 |
|---|---|---|
| v1 核心 | ~2000 | 已有 |
| 205 业务模块 | ~2500 | 已有 |
| HTTP 适配器 | ~800 | 已有 |
| Web 前端 | ~3000 | 已有 |
| **Qt 门面** | ~300 | P1 |
| **Qt 界面** | ~4000–6000 | P1–P2 |
| 双前端一致性维护 | 持续 | 隐性 |

结论："一套底层随时切前端"成立；"开发量减半"不成立——**核心共享，界面两份**。

### 风险

| 风险 | 后果 | 对策 |
|---|---|---|
| 两端功能不同步 | 客户质疑"以哪个为准" | 能力矩阵；对外只承诺核心契约 |
| Qt 侧没有自动化 | 越做越不敢改 | P3 的最小 QtTest 冒烟 |
| 门面复制业务逻辑 | 两套语义，早晚漂 | 四条硬规矩（§6.2） |
| Qt 渗进底座 | 第三个前端就难了 | `Core` 只认 `EventSink`；门面独立目录 |
| 两端都只做一半 | 都不可交付 | 先定交付主线；Qt 按 P1→P2 走 |

## 九、让"随时切前端"成立的四个前提

1. **契约单一来源**：命令名/参数形状/错误码只在 `Core` 定义一次；
2. **门面不越权**：只翻译，不做决策；
3. **核心零 Qt**：底座不 include 任何 Qt 头文件；
4. **测试分层**：核心用 HTTP 脚本测（与 UI 无关），UI 各自冒烟测。

四条里第 1 条最容易破——只要有人图省事在门面里加一条业务判断，就开始漂了。

## 十、一页结论

| 问题 | 回答 |
|---|---|
| 这策略对吗 | 对。它是兜底 + 降风险的组合，商业上也有主动权 |
| 最大收益 | 有一个原生 Qt 版本可交付；核心只写一遍 |
| 最大误解 | "Qt 验证完，Web 调一下就好"——表现层要重写，只是不担业务风险 |
| 信心从哪来 | HTTP 层自动化测试，不是第二个 UI |
| 最小可交付 | P1：连接 + 测量 + 结果 + 导出，1 天 |
| 一句话 | 核心一套、界面两套；Qt 兜底排障，Web 体验演示 |
