# 双前端策略：Qt QWidget 与 Web 共用一套内核

> 2026-11-13
> 背景：CEF 这条路线传统客户未必接受，团队也没有先例。设想是——同时支持
> 原生 Qt 界面和 Web 界面，核心保持零 Qt，随时可切换前端；先用 Qt 验证真实功能，
> 验证好了 Web 那边"调试一下"就完成。

---

## 一、先把意图说准

我理解你要的是三件事，按重要程度排：

1. **降风险**：不把交付押在一个没做过的形态上（CEF）。
2. **有兜底**：真到客户不接受浏览器/嵌入引擎时，能拿出原生 Qt 版本。
3. **一套内核**：设备协议、作业、判定、存储只写一遍，两个前端共享。

第 4 件事（"Qt 验证完，Web 调一下就好"）是这套策略的**推论**，不是它的收益——
下面会说明为什么这个推论需要修正。

---

## 二、结论

**策略成立，值得做。但收益要重新排序。**

- 真正的收益是 **2（兜底）> 1（降风险）> 3（复用）**；
- "Web 那边调试一下就好"这个预期偏乐观：Web 前端不是"调一下"，
  它是一次完整的表现层实现，只是**不承担业务风险**；
- 你最该建立的信心**不在第二个 UI 上，而在核心的自动化测试上**——
  这一点下面单开一节讲。

---

## 三、这个策略真正买到了什么

### 1. 兜底交付（最实在）

客户说"我们不上浏览器/不允许装嵌入式浏览器"，你有东西可交。
这不是技术问题，是商业问题——有两个形态，销售话术就变成
"同一套内核，界面您选"，主动权在你这。

### 2. 核心验证链路短

Qt 是你熟的领域。核心有 bug 时，你能在 Qt Creator 里几秒钟断到现场，
而不是"打开 DevTools → 看 Network → 猜是服务端还是页面"。
**用熟悉的工具定位核心问题，效率高一个数量级。**

### 3. 前端可切，作为架构性质而不只是口号

核心零 Qt 已经在 CEF 客户端上兑现过一次（那个客户端一行 Qt 都没有）。
所以"再加一个 Qt 前端"在架构上是顺的，不需要额外发明什么。

### 4. 多出来的消费者

核心做成库之后，除了两个 UI，还能被 CLI、自动化测试台、甚至产线脚本直接调用。
这在工控项目里经常用到（产线自检、批量校准）。

---

## 四、这个策略买不到什么

### 1. Web 的表现层风险，Qt 一样都测不到

两个前端共享的是**核心**，不共享**表现**。Web 的问题几乎全在表现层：

| 类别 | 例子 |
|---|---|
| 布局 | 1024×768 下表格溢出、高 DPI 下错位 |
| 交互 | 输入法、焦点、拖拽、键盘快捷键 |
| 时序 | 事件风暴、重绘卡顿、WS 断线重连 |
| 环境 | CEF 版本差异、GPU 不可用、字体缺失 |

这些在 Qt 上跑一万遍也发现不了。所以"Qt 验证好了 → Web 调一下"这个链条，
**只能省掉业务逻辑的调试，省不掉界面本身的调试**。

正确的说法是：**核心验证一次，两端各自只承担表现层风险。**

### 2. 界面要写两遍，这是最大成本

205 的 web 界面约 3000 行。同样的功能用 Qt Widgets 重写，因为控件更啰嗦、
信号槽样板更多，估计 4000~6000 行。这还没算两边的联调。

### 3. 一致性负担

两端一旦不同步，就会出现"同一个功能，web 有、Qt 没有"的尴尬。
客户会问："你们说的功能到底以哪个为准？"

---

## 五、三个层次的分工（这是让策略成立的关键）

不要把两个 UI 当平等公民。分成三层，职责写死：

```text
┌─────────────────────────────────────────────────────┐
│ 表达层   Web UI            Qt UI                     │
│         只管呈现与交互      只管呈现与交互            │
│         两个实现，可以不同步                          │
├─────────────────────────────────────────────────────┤
│ 契约层   Core 的命令/参数/作业/错误码                 │
│         唯一真相来源；用 HTTP 脚本测                 │
├─────────────────────────────────────────────────────┤
│ 内核     v1::Core + 业务模块（零 Qt、零浏览器）       │
└─────────────────────────────────────────────────────┘
```

- **契约层**：改一个命令，两端都得跟着改——这是唯一必须同步的地方；
- **表达层**：允许不同步，允许一端先有。但要有一张"能力对照表"，
  对外统一口径。

---

## 六、关于"心里没底"这件事

这句是整段话里最该认真对待的，但解法要换。

**两个 UI 不能给你对核心的信心，自动化测试才能。**

理由：你手动用 Qt 界面点十遍，覆盖的是你想到的十条路径；
而 205 现在那套 HTTP 脚本（`eph205_api_test.py` / `eph205_e2e.py`）
每次改动都跑一遍，覆盖的是全链路：登录 → 连接 → 导入 → 测量 → 落库 → 导出。

所以正确的"建立信心"的顺序是：

1. 核心 + HTTP 适配器（已完成）—— **脚本化的信心来源**；
2. Qt 界面 —— **兜底交付物 + 你熟悉的排障入口**；
3. Web 界面 —— **面向接受浏览器的客户**（205 已有）。

换句话说：**Qt 前端的作用是"能交付 + 好排障"，不是"用来验证核心"。**
把这句话摆正，后面的取舍就都清楚了。

---

## 七、成本量化

| 部分 | 行数量级 | 状态 |
|---|---|---|
| v1 核心（帧/会话/作业/静态/模块路由） | ~2000 | 已有 |
| 205 业务模块（协议/串口/仿真/存储） | ~2500 | 已有 |
| HTTP 适配器 | ~800 | 已有 |
| Web 前端 | ~3000 | 已有 |
| **Qt 门面**（每个模块一个） | ~300 | 待做 |
| **Qt 界面**（同功能集） | ~4000–6000 | 待做 |
| 双前端一致性维护 | 持续 | 隐性成本 |

可以看到：**核心是共享的，界面是两份**。所以"一套底层随时切前端"这句话成立；
"开发量减半"这句话不成立。

---

## 八、风险清单与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| 两端功能不同步 | 客户质疑"以哪个为准" | 维护一张能力对照表；对外只承诺核心契约 |
| 只有 web 有 e2e，Qt 没有自动化 | Qt 回归靠手点，越做越不敢改 | 给 Qt 写最小 QtTest 冒烟（连接→测量→结果），覆盖主链路即可 |
| 门面把业务逻辑复制一份 | 两套语义，早晚漂 | 门面只做 JSON↔结构体翻译，禁止绕过 `Core::Handle` |
| Qt 依赖渗进底座 | 底座不再"零 Qt"，第三个前端就难了 | 门面独立目录；`Core` 只认 `EventSink` 接口 |
| 两边都只做一半 | 都不可交付 | 先定"哪一端是交付主线"，另一端按里程碑补 |

---

## 九、建议的推进顺序

| 阶段 | 内容 | 产出 |
|---|---|---|
| 1 | 抽 `Core` + `EventSink`（纯重构，半天） | 现有 HTTP/测试全绿 |
| 2 | 写 `Eph205Device` 门面 + Qt 最小页面（连接/测量/结果） | **能演示、能兜底** |
| 3 | 补齐 Qt 页面（调试/历史/工具） | Qt 版可交付 |
| 4 | 两端能力对照表 + Qt 冒烟测试 | 一致性可控 |
| 5 | （可选）把 web 端按客户反馈打磨 | — |

注意阶段 2 只做最小闭环——**先让"兜底"这件事成立，再谈完整**。
真要临时交付，一个能连接、能测、能出结果的 Qt 界面就够用了。

---

## 十、让"随时切前端"成立的四个前提

这四条不满足的话，"随时切换"就是口号：

1. **契约单一来源**：命令名、参数形状、错误码只在 `Core` 里定义一次；
2. **门面不越权**：门面翻译，不做决策（权限、校验都在 Core）；
3. **核心零 Qt**：底座不 include 任何 Qt 头文件，靠 `EventSink` 解耦；
4. **测试分层**：核心用 HTTP 脚本测（与 UI 无关），UI 各自冒烟测。

---

## 十一、一页结论

| 问题 | 回答 |
|---|---|
| 这策略对吗 | 对。它是降风险 + 兜底的组合，商业上也有主动权 |
| 最大收益是什么 | 有一个原生 Qt 版本可交付；核心只写一遍 |
| 最大误解是什么 | "Qt 验证完，Web 调一下就好"——表现层要重写，只是不担业务风险 |
| 信心从哪来 | 从 HTTP 层自动化测试来，不是从第二个 UI 来 |
| 值得投入吗 | 值得，但建议 Qt 先做**最小闭环**（能测能出结果），别一上来做全套 |
| 一句话 | 核心一套、界面两套；Qt 负责兜底和排障，Web 负责体验和演示 |
