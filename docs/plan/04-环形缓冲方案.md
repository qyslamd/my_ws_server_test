# 环形缓冲实现方案：把缓冲从业务挪回通讯层

> 2026-11-17（v5：给 state 补每 tick 的帧数/字节双上限与公平轮转；
> v4：删掉订阅时的窗口强制校验——它和默认值体系冲突，
> 改为在流清单里给每个流发 `maxFrameBytes`，由客户端自己选 `window`；
> v3 补描述符内存上限与预算口径，写明"可用配额必须逐帧重算"；
> v2 补 overrun 上报时序、通知帧 `seq` 取值、销毁时序、锁延迟门槛与内存总量上限）
> 背景：协议文档 `docs/spec/02-ws-protocol-v1.md` 已经规定"来不及发送要丢最旧的
> 完整帧，并且必须上报 `core.overrun`"，但通讯层至今没有缓冲层，这条规范落不了地。
> 本文只讲怎么把缓冲层做出来，不含代码。

---

## 一、现在为什么没有

先说清楚现状，不然后面的设计没有靶子。

今天的数据路径：

```text
模块工作线程
   └─► readings_（std::deque，上限 4096 条，满了静默丢）
          ▲
          │ 每 10 毫秒，事件循环调一次 Produce()
          │ 每次最多取 64 条，打成一块 RECORDS
      服务端 Tick()
          └─► 有额度才发；没额度就不取数
```

三个问题都出在这条链上：

1. **缓冲在模块里，不在通讯层。** 淘汰规则是"丢最旧的 json"，没有序号、没有统计，
   丢了也没人知道。
2. **采集线程没有被保护。** Tick 每 10 毫秒只取 64 条，链路一慢、额度一耗尽，
   Tick 干脆不调 `Produce()`，数据全堆在模块的队列里，4096 条一到就开始丢——
   丢在业务代码里，通讯层看不见。
3. **`seq` 在发送前才分配。** 被丢掉的数据从来没占过号，客户端看到的序号是连续的，
   于是"数据少了"这件事在协议层面永远发现不了。

结论：缺的不是一个容器，而是"缓冲搬到通讯层、按整帧淘汰、淘汰要占号、淘汰要上报"
这一整套语义。

## 二、目标行为

规范里写死的五条，实现时逐条对应：

| # | 要求 | 出处 |
| - | ---- | ---- |
| 1 | 业务线程写缓冲不被卡住 | §8.1 第 1 条 |
| 2 | 写满淘汰最旧的完整帧，不许只覆盖半帧 | §8.1 第 2 条 |
| 3 | 配额决定何时发，用完就暂停，不丢数据 | §8.1 第 4 条 |
| 4 | 淘汰要发 `core.overrun`，带 `firstSeq`/`lastSeq` | §8.3 |
| 5 | 没人订阅时不入队、不占号、不报溢出 | §8.1 第 7 条 |

## 三、核心数据结构

### 3.1 一个流一个字节环

每个订阅流一份，挂在 `Session::subs` 里：订阅时分配，退订或会话结束时释放。
容量取 `limits.buffer_bytes[cls]`，`sample` 4 MiB、`record` 8 MiB（规范 §8.4）。

内部三样东西：

| 组件 | 类型 | 作用 |
| ---- | ---- | ---- |
| 字节区 | `std::vector<uint8_t>` | 长度正好是容量，之后不再增长 |
| 帧描述符 | 队列，每条记录起始位置、长度、`seq`、`ts` | 淘汰和读取都以"整帧"为单位 |
| 读写指针 | 两个单调递增的计数器 | 取值时对容量取模 |

用单调计数器而不是"取模后的下标"，是为了让「已用字节 = 写指针 − 读指针」永远成立：
不用单独维护长度，绕圈时也不会出现"满了还是空了"的歧义。

**描述符也是有成本的，必须单独封顶。** 每条描述符 24 字节（位置 8 + 长度 4 + 序号 4
+ 时间戳 8）。字节区装得下的帧数取决于帧有多小：8 MiB 的缓冲配 32 字节的小帧，
能塞进 26 万条描述符，光这一项就是 6 MiB——比很多流的整个缓冲还大。
所以每个流再压一条硬上限：

```text
描述符数量 <= min(字节容量 / 最小帧长估计, kMaxFrames)
kMaxFrames = 65536        // 每流最多 65536 条，占 1.5 MiB
```

超过 `kMaxFrames` 时，按"淘汰最旧一帧"处理，计入 `core.overrun` 的统计。
这样内存有上界，小帧场景也不会把元数据撑爆；而且它本来就是对的——
小帧多到描述符都记不下时，旧帧本来就该丢。

**跨环尾**（一帧从尾部写到头部）是常态，不是异常。写入和读出都按"最多两段 memcpy"
处理，既不浪费尾部空洞，也不镜像双倍内存。

### 3.2 写入：先腾地方，再写

```text
1. 单帧比整个环还大 → 拒收，返回 false
2. 已用字节 + 本帧长度 > 容量 → 循环淘汰最旧的整帧，每淘汰一帧记一次统计
3. 分配 seq（服务端的计数器自增）
4. 拷贝进环，追加描述符，写指针前进
```

关键点：第 2 步淘汰的是**已经在环里的旧帧**，不是拒收新帧。这决定了"旧的丢、新的保"，
也就是规范说的"写满覆盖最旧数据"。

### 3.3 读取：按配额取

发送侧每次取帧前算可用配额：

```text
可用 = window − 已发未归还       （结果为负时按 0 处理）
```

从环头取一帧，长度不超过可用配额就发，并从配额里扣掉这一帧的负载字节数
（不含帧头和块头）。

**每取一帧都要重算一次可用配额，不许在循环外面算一次。** 这条不是废话：
环形缓冲一次 Tick 通常要连发好几帧，如果只在进循环时算一次 `可用`、
循环里却每帧都加 `已发未归还`，那么"发一批"就变成"按第一批的额度发到底"，
欠账就会真的累积起来。写成"取一帧 → 发 → 扣账 → 重算 → 再取"，
这个隐患从结构上就不存在。

一处边界：环头的帧比可用配额还大时，**允许超发这一帧**，否则客户端把 `window`
设小一点，整条流就卡死了。但超发必须有界，而且不能变成常态：

- 只有 `已发未归还 == 0`（此刻一次都没欠）时才允许超发。只要已经欠着，就继续等配额，
  不许再超发。这条闸门保证欠账永远不超过一帧，不会滚雪球。

  > 把这道闸门走一遍就清楚了。设 `window = 1 MiB`、单帧 `2 MiB`、客户端一次都不还：
  > 第 1 个 Tick：可用 1 MiB > 0，超发一帧，已发未归还 = 2 MiB；
  > 第 2 个 Tick：可用 = 1 MiB − 2 MiB < 0，按 0 处理，直接不发。
  > 之后每个 Tick 都一样不发，直到客户端归还配额。
  > 所以欠账的上界是 `window + 一帧`，与 Tick 的次数无关——
  > 能累积的前提是"可用配额为 0 时仍然发"，而这里明确禁止。

- **不做窗口大小的强制校验。** 单帧大于 `window` 时只是退化成"一个归还周期发一帧"，
  不会卡死，也不会累积欠账（闸门已把上界压在 `window + 一帧`）。
  拿 422 去拒订阅，代价是默认路径全灭：`default_window` 是 1 MiB、`max_data_frame`
  是 8 MiB，按"两倍帧长"校验，所有不传 `window` 的客户端都会被拒掉。
  用重复防御换默认路径的可用性，不划算。
- 客户端要选合适的 `window`，得先知道面对的帧有多大：`GET /streams` 的每个流都带
  `maxFrameBytes`，取它的两倍作为 `window` 是稳妥值。服务端只给建议，不做强制。
- 单帧超过 `max_data_frame` 属于协议错误，入环时按 3.2 第 1 条拒收，不要指望超发兜住。

### 3.4 溢出的记录与合并

淘汰时先累计：丢了几帧、几字节、被丢掉的那段 `seq` 从哪到哪。上报分两种时机：

- **第一次溢出立刻报。** 不进入合并窗口，下一个发送周期就发出去。
- **同一段持续溢出才合并。** 上一次已经报过、500 毫秒内又发生淘汰，把区间延长，
  到期再报一条。

规范里这两句本来就是拧着的：§8.1 第 5 条要求"覆盖最旧帧**的同时**发通知"，
§8.3 又要求"每个流 500 毫秒内合并成一条"。按上面的分法两者同时满足：
第一声是即时的，后续才是合并的。

> 注意"立刻"的落地位置：上报只能发生在事件循环里，不能在生产的那个线程发。
> mongoose 的发送不是线程安全的。所以"立刻"= 下一个 `Tick`（≤10 毫秒），
> 不是真正的零延迟。生产中线程只负责置一个待报标记和累计统计。

到点发两条：

1. `core.overrun` 事件（JSON）；
2. `opcode=ERROR` 的一帧（规范 §8.3 要求，保证事件通道拥挤时也一定看得到）。

两处内容一致。

**ERROR 帧的 `seq` 固定为保留值 `0`。** 不能用"该流当前序号"——那样它就和刚发出去的
最后一帧数据同号，两条帧的 `(streamId, seq)` 完全相同；客户端无论按序号去重还是做
缺口统计，都会被这条通知帧带偏。用 `0` 这一层意思很清楚：这条帧不占号、不推进、
不参与缺口判定，也不吃配额。

> 规范 §8.3 现在写的是"`seq` = 该流当前的序号"，要同步改成"`seq` = 0（保留值）"。
> §7.2 的字段说明也要补一句"`seq = 0` 只出现在通知帧上"。

连续淘汰的区间要能合并：两次上报之间又丢了帧，`firstSeq` 保持、`lastSeq` 往后延，
最终只报一段区间，而不是一串碎片。

## 四、接口改动：从"拉"改成"推"

这是本方案唯一的破坏性改动。

现在的 `Module::Produce()` 是"服务端来要，模块给一批"。问题在于服务端只在有配额时
才来要，之前的缓冲全压在模块里。要让缓冲真正落在通讯层，数据的产生必须由模块主动推进来。

```cpp
struct Record {
  uint64_t ts_ns;
  std::vector<uint8_t> payload;
};

// 送给业务模块的推送口。线程安全、不阻塞：内部只持短锁，不等网络。
class StreamSink {
 public:
  // sample 类：一个负载就是一帧
  bool PushSample(uint32_t stream_id, const uint8_t* data, size_t len);
  // record 类：一批记录打成一帧，通讯层负责编码 RECORDS 块
  bool PushRecords(uint32_t stream_id, const std::vector<Record>& records);
  // state 类：只保留最新值，不占号、不排队
  void SetState(uint32_t stream_id, const uint8_t* data, size_t len);
};
```

返回 `false` 的含义：当前没人订阅、流不存在、或者单帧超大，这次数据被丢掉了。
模块可以据此计数、写自己的日志，但**不许重试、不许等待、不许反过来卡住采集**。

模块通过一个带默认空实现的钩子拿到这个口子：

```cpp
virtual void AttachSink(StreamSink* /*sink*/) {}
```

默认空实现意味着现有模块不改也能编译，只是不推送。迁移可以一个模块一个模块地做。

> 为什么不用一组回调函数指针：同一时刻只有一个口子，而且它有生命周期
> （会话结束就失效），一个对象指针比一组回调好管。

## 五、服务端集成

### 5.1 生命周期

订阅成功时分配环、登记到 `Session::subs`；退订或会话结束时释放，连同累计的溢出统计。

没有人订阅时，`Push` 直接返回 `false`，不入队、不占号，对应规范 §8.1 第 7 条。

**销毁必须先断生产，再放内存。** 模块的采集线程还在跑的时候把环析构掉，
是典型的用后释放（use-after-free），而且只在断线那一瞬间偶发，最难复现。
固定三步，顺序不许调：

```text
1. 标记 sink 已失效（同一个临界区里把环标记为 detached）
   → 此后的 Push 立刻返回 false，绝不再碰环里的任何字节
2. 停模块：SAFE_STOP → on_session_end → 等采集线程退出
3. 释放环，连同累计的溢出统计一起丢弃
```

第 1 步和第 2 步之间会丢掉一点在途数据，这是有意的：会话已经结束，
这些数据发不出去，留着只会让"谁还持有环"变得难判断。

> 为什么不是先停模块再标记：停模块需要时间，这期间采集线程照常 Push；
> 先标记能把窗口压到"同一个临界区"，不用去推理线程退出的时机。

### 5.2 `seq` 的归属

计数器在服务端，每个流一个，跟着会话走。会话结束就重置——这与"重连是全新会话"
一致，客户端本来就把订阅后的第一帧当基准。

**序号只能在入环时分配，不能在发送时分配。** 这正是本轮修订 §7.7 的原因。

### 5.3 与现有发送路径的关系

`Tick()` 仍是 10 毫秒一次，但职责变成两件：把环里能发的帧按配额发出去；
取溢出统计，到点就报。

发送队列 64 MiB 上限和心跳积压保护保留不动，它们退化成最后一道保险：
正常情况下配额会先让队列慢下来，轮不到它们出手。

## 六、state 类的特例

`state` 不进环，只存一份最新值加一个"脏"标记。

发送时：有订阅、值变了，才分配 `seq` 并发出去。合并发生在分配之前——同一个 10 毫秒内
的十次变化只发一次、只占一个号，客户端也就不会看到假的序号断档。

这条与规范 §7.7 的写法一一对应。

**state 也要有总闸，否则一条流抽风能拖垮整场会话。**

`state` 不过环、不过配额，帧是直接进共享发送队列的。如果某个模块以 10 kHz 刷状态，
队列会被 state 帧占满，然后走 §8.5 的溢出停机——所有流、整个会话一起结束。
脏标记合并把单流的常态压到每 10 毫秒一帧，但流数没有上限，叠加起来就没有边界了。

所以给 state 单独设一道发送闸，每 tick 卡两个数：

```text
每 tick 最多 8 帧 state（所有流合计）
每 tick 最多 256 KiB state 负载（所有流合计）
```

超出的推迟到下一个 tick。推迟不违反任何承诺：state 本来就只保证最终一致，
而"推迟"的实现就是保留最新值——下一个 tick 发出去的自然是最后那个值，中间值该丢就丢。

两个配套细节：

- **公平轮转**：每次从上次停下的位置往后发。否则固定从第一路开始，后面的 state 流
  永远抢不到名额，会一直饿着。
- **两个上限都要有**：只卡帧数，遇到大帧照样能把队列撑爆；只卡字节，
  小帧会把 CPU 和帧头开销拉满。

**取值和清脏必须在同一把锁里做完。** 正确顺序是：进锁 → 拷贝值且清脏标记 → 出锁 → 发帧。
反过来（先读值、放锁、再清脏）会有一个窗口：生产者恰好在这个窗口里写入了新值时，
新值被清脏动作一起吞掉，客户端永远看不到它，而且没有任何报错。这种丢值最难查。

> 这是一个"必须写进实现约定"的点，不是实现细节：`SetState` 与取数两侧共用主流锁，
> 不允许为了省一次加锁把清脏拆到锁外。

## 七、线程与锁

参与者只有两类：模块的工作线程（写）和事件循环（读）。

每个流一把普通互斥锁，读写都持锁。锁里只做 memcpy 和队列操作，**不做 IO、不做 JSON 编码**。

> 为什么不无锁：一生产者一消费者的无锁环更快，但这里丢不起的是正确性；
> 而且每帧只有几 KB，锁的持有时间是微秒级，不是瓶颈。

一条硬规矩：绝不持环的锁去调 mongoose 或模块回调。发帧之前先拷出来、放锁、再发。

**"微秒级"要有数，不能只是感觉。** 方案给两条可以写进验收的门槛：

| 指标 | 门槛 | 怎么量 |
| ---- | ---- | ------ |
| 单次持锁时间 p99 | < 50 µs | 调试构建里在加锁处打时间戳，跑压力用例后导出直方图 |
| 单次持锁时间 p99.9 | < 200 µs | 同上 |
| 超时异常 | 任何一次 > 5 ms 都算缺陷 | 同上，命中时打一条日志带帧长 |

压力用例用第十章的 20 MB/s 场景，跑十分钟取分布。指标不达标先查是不是在锁里
做了拷贝之外的活（JSON 编码、日志、内存分配），而不是急着换无锁结构。

## 八、内存

按默认值算，两个流同时在推，**要把描述符和临时缓冲一起算进去**：

```text
字节区      sample 4 MiB + record 8 MiB            = 12 MiB
描述符      每流上限 65536 条 × 24 B，两个流        ≈  3 MiB
发送拷贝    单块 max_data_frame，事件循环里复用一块 =  8 MiB
                                        合计上限   ≈ 23 MiB
```

只算字节区会低估一半以上。尤其是描述符：小帧场景下它和字节区是同一个量级
（见 3.1 的算法），必须跟着一起算预算。

这个量级可以接受，但**总量上限 v1 就要有**，不能留到以后。

一条会话里所有环加起来不超过 `limits.ring_total_bytes`（默认 64 MiB）。
**这个数算的是"字节区 + 描述符"的合计，不是只有字节区**。
订阅时先算"当前已用 + 本次要的容量"，超了直接拒绝，返回 `409` + `2006`，
`msg` 里写明是缓冲总量不够，并在能力接口里把已用/上限一起暴露出来。

> 为什么不是"以后再说"：环的容量是客户端间接影响的（订阅哪个流、订阅几个），
> 一个写坏的客户端反复订阅退订，或者以后某个模块一口气声明几十个流，
> 内存就会在没人注意到的情况下涨上去。上限是几行代码，留白是事后排查。

---

## 九、分五步落地

每一步都能单独验证，每一步做完仓库都还是能跑的状态。

| 步骤 | 内容 | 完成标志 |
| ---- | ---- | -------- |
| 一 | 环形缓冲本体：`StreamRing` 类，写入、淘汰、跨环尾、统计 | 单元测试把边界打透，行为零变化 |
| 二 | 推送口与写入路径：`StreamSink`、`AttachSink`、分配环、入环分配 `seq` | 新旧路径并存、开关可回退，且双轨一致性用例通过 |
| 三 | 发送侧改造：`Tick` 从环里取数，接上 `core.overrun` 与 ERROR 帧 | 端到端能观测到溢出 |
| 四 | 模块迁移：eph205 删掉 `readings_`，改调 `PushRecords` | 模块里那个 4096 条静默丢弃消失 |
| 五 | 删掉 `Produce` 与过渡开关 | 只留一条路，不给后人留坑 |

## 十、验收

**单元测试**（第一步就要写）：

- 写满后淘汰最旧，且被淘汰的帧序号连续；
- 跨环尾写入再读出，内容逐字节一致；
- 单帧大于容量时拒收；
- 连续淘汰时 `firstSeq`/`lastSeq` 合并正确；
- 空环取数返回"没有数据"，不崩；
- 第一次溢出在下一个发送周期就被报出（不是等 500 毫秒）；
- 通知帧的 `seq` 恒为 `0`，且不推进该流计数器；
- `window` 小于单帧时订阅照常成立，只是退化成"一周期一帧"，不卡死、不报错；
- `state` 高频写、高频取跑十万次，最后一次写入的值一定被发出（不许被吞）；
- state 洪泛：模拟 20 个 state 流每个 tick 都变，每 tick 的 state 发送量与字节数
  都守在上限内，且每一路都轮得到，没有被永久饿死的流；同时 record 流不受影响；
- 超发边界：`window` 小于单帧、客户端一直不还配额，连跑一百个发送周期，
  已发未归还只涨到"window + 一帧"就停住，不许逐周期累加；
- 描述符上限：用 32 字节的极小帧灌满一个流，描述符数量停在 `kMaxFrames`，
  多出来的按溢出计入统计，进程内存不继续增长。

**双轨期专项测试**（第二步引入了新旧两条路，必须专门测，不能靠"看起来能跑"）：

- 同一段数据分别走 `Produce` 和 `Push`，产出的帧逐字节一致；
- 运行中来回切换开关，数据不断流、序号不重复也不跳号；
- 开关处于"旧路"时，环不分配、内存不增长。

**端到端**（第三、四步之后）：

用一个不归还配额的裸 WS 客户端订阅并持续推数据，预期依次看到：
`core.overrun`（带真实序号区间）→ `opcode=ERROR` 的同内容帧；
客户端补上配额后数据继续流动，序号从断点往后接。

**压力**：

生产者按 20 MB/s 推、客户端每 100 毫秒归还一次配额，跑十分钟，
看内存曲线是否平稳、序号是否单调、有没有漏报的溢出。

**销毁竞态**：采集线程全速 Push 的同时，让客户端反复断开重连两百次。
通过标准是进程不崩、调试构建的泄漏检查在退出时干净、没有残留的环。
这个用例专门盯 5.1 那三步的顺序，是本方案里唯一"错了也不会立刻报错"的地方。

## 十一、风险与取舍

| 风险 | 说明 | 缓解 |
| ---- | ---- | ---- |
| 从拉改推会动到所有模块 | 接口签名变了 | `AttachSink` 有默认空实现，先只迁 eph205，其余模块保持原样也能跑；双轨一致性用例兜住迁移期 |
| 容量与配额配错 | 配额小于单帧会频繁触发"超发一帧"；配额远大于容量则环先满 | 流清单给出 `maxFrameBytes` 供客户端选值；服务端不做强制校验（强制会误伤默认路径） |
| 序号在会话之间重置 | 现在的单会话模型没问题，多客户端时要重新定义 | 留到 §16 的多客户端议题里一起做 |
| 内存无上限 | 订阅哪个流、订几个由客户端决定，模块以后可能声明更多流 | 第八节的 `ring_total_bytes`，v1 就落地，不留到以后 |
| 描述符吃光内存 | 小帧场景下每帧 24 字节描述符，8 MiB 缓冲能装 26 万条，比字节区还大 | 每流 `kMaxFrames` 上限，超出按淘汰处理；描述符计入预算（3.1、第八节） |
| 欠账累积的实现变体 | 如果"可用配额"在循环外只算一次，一批几帧就会连续超发 | 3.3 写死"取一帧、发、扣账、重算"，并有专项用例 |
| state 洪泛连坐全场 | state 不过配额，模块刷得勤就能把共享发送队列占满，触发 §8.5 停机，所有流陪葬 | 第六节的每 tick 帧数/字节双上限 + 公平轮转；有专项用例 |
| 销毁时序写反 | 先放内存后断生产 = 用后释放，只在断线瞬间偶发，最难复现 | 5.1 的三步顺序 + 销毁竞态压力用例 |
| 通知帧 `seq` 取值 | 沿用"当前序号"会和最后一帧数据同号，破坏客户端的去重/缺口判断 | 改为保留值 `0`，并同步修订规范 §8.3、§7.2（见第十三节） |

---

## 十二、明确不做

- 不引入无锁队列；
- 不做跨流优先级；
- 不做落盘与断线补发（规范 §16 已列为 v1 之外）；
- 不做动态扩容：容量在订阅时定死，改容量等于重新订阅。

## 十三、需要同步修订规范的五处

本方案改了几处协议行为，规范要跟着动。这些改动不影响帧的二进制结构，
只影响字段取值和文字表述，现有客户端不受影响（通知帧的 `seq` 目前还没人依赖）：

| 规范位置 | 现状 | 改成 |
| -------- | ---- | ---- |
| §8.3 `ERROR` 帧 | `seq` = 该流当前序号 | `seq` = `0`（保留值，不占号不推进） |
| §7.2 `seq` 字段说明 | 只说"该流内递增的序号" | 补一句"`seq = 0` 只出现在通知帧上，不参与缺口判定" |
| §8.1 第 5 条 | "覆盖旧帧的**同时**发通知" | 与 §8.3 统一：首次溢出立即报，同一段持续溢出才 500 毫秒合并 |
| §8.2 | 没写"单帧大于配额时允许超发一帧"这条边界 | 补进去，并写明**不做窗口强制校验**，只给取值建议 |
| §6.4 流清单 | 每个流没有帧长信息，客户端无法估算 `window` | 每个流加 `maxFrameBytes` 字段 |
| §8.1 第 6 条 | 只说 state 不参与配额，没提它另有发送闸 | 补一句"每周期对全部 state 流合计限帧数与字节数" |
| §8.4 | 没有缓冲总量上限 | 补 `ring_total_bytes`（默认 64 MiB）与超限时的行为 |
